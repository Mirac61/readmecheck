# README criteria

readmecheck uses 23 deterministic rules. Nothing is generated by an LLM. A rule
returns **pass**, **fail**, or **skipped**; skipped checks are removed from the
score rather than treated as failures.

## How scoring works

Each rule has a fixed weight. A category score is:

```
round(100 × passed weight / (passed weight + failed weight))
```

Skipped rules contribute to neither side. The overall score combines all
categories the same way. Grades are **A** ≥ 90, **B** ≥ 80, **C** ≥ 70,
**D** ≥ 60, and **F** below 60. Category scores are shown separately so a strong
set of metadata checks cannot hide broken links or missing usage instructions.

Weights reflect impact on a first-time visitor, not implementation effort.
"README exists", installation, usage, license, and broken relative links carry
the most weight. Informational checks such as topics and archived status carry
little or no scoring pressure.

The rule set is grounded in these public guides:

- [Make a README](https://www.makeareadme.com/)
- [Awesome README](https://github.com/matiassingers/awesome-readme)
- [Open Source Guides: Starting a project](https://opensource.guide/starting-a-project/#writing-a-readme)
- [GitHub: Classifying repositories with topics](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/classifying-your-repository-with-topics)
- [GitHub: Licensing a repository](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)
- [Choose a License](https://choosealicense.com/)
- [GitHub: Adding a workflow status badge](https://docs.github.com/en/actions/monitoring-and-troubleshooting-workflows/adding-a-workflow-status-badge)
- [GitHub: About workflows](https://docs.github.com/en/actions/using-workflows/about-workflows)
- [GitHub: Creating Mermaid diagrams](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams)
- [GitHub: Setting guidelines for repository contributors](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/setting-guidelines-for-repository-contributors)
- [GitHub: Archiving repositories](https://docs.github.com/en/repositories/archiving-a-github-repository/archiving-repositories)
- [W3C WAI: An alt decision tree](https://www.w3.org/WAI/tutorials/images/decision-tree/)
- [WCAG 2.2: Non-text content](https://www.w3.org/WAI/WCAG22/Understanding/non-text-content.html)

Heading matching is deliberately bilingual. It recognises English and German
variants (for example Installation/Einrichtung, Usage/Verwendung,
Prerequisites/Voraussetzungen, Contributing/Mitwirken,
License/Lizenz). Matching is case-insensitive and word-aware after punctuation
is normalised.

## Rules

### Basics

| ID | Severity | Weight | What passes |
| --- | --- | --- | --- |
| `readme-exists` | error | 12 | A non-empty README is returned for the repository. |
| `top-level-title` | error | 6 | The README contains an H1 title, either Markdown or HTML. |
| `description-paragraph` | warning | 7 | A prose paragraph of at least five words appears before the first H2. |
| `repo-description` | warning | 5 | GitHub's repository description is non-empty. |
| `topics` | info | 2 | At least one repository topic is set. |

**readme-exists.** The README is GitHub's de facto project landing page; without
it a visitor gets an unexplained file listing. The check treats a missing file
and a whitespace-only file as failures. Source: GitHub About READMEs, Open Source
Guides.

**top-level-title.** A single H1 names the project and provides a heading for the
rendered page and assistive technology. The parser accepts Markdown H1s and
simple HTML `<h1>` elements, but does not accept H2-only or bold-only titles.
Source: Make a README, standard-readme.

**description-paragraph.** Badges, logos, and a title make a poor introduction.
The check skips image-only paragraphs and requires at least five visible words
before the first H2. HTML images do not contribute fake prose. Source: Make a
README, Awesome README.

**repo-description.** The GitHub About description appears in search results,
repository cards, and link previews. It needs to explain the project
independently of the README. Source: GitHub About READMEs, GitHub repository
metadata guidance.

**topics.** Topics are GitHub's discovery vocabulary. The rule is informational
because a project can be excellent without them. Source: GitHub topics
documentation.

### Getting started

| ID | Severity | Weight | What passes |
| --- | --- | --- | --- |
| `installation-section` | error | 8 | A non-empty installation/setup/getting-started heading exists. |
| `usage-section` | error | 8 | A non-empty usage/how-to-use heading exists. |
| `code-example` | warning | 6 | A non-empty fenced code block has a language tag. |
| `prerequisites` | info | 3 | A prerequisites heading/mention exists. |

**installation-section.** Installation is the first practical barrier for a new
user. Headings such as Installation, Setup, Getting Started, Einrichtung,
Installieren, and Schnellstart are accepted. A heading followed directly by
another heading fails. Source: standard-readme, Make a README.

**usage-section.** A README should show the smallest useful invocation after
installation. Usage, How to use, Using, Verwendung, Benutzung, Nutzung,
Anwendung, and similar headings are accepted. Source: standard-readme, Make a
README.

**code-example.** Fenced code with an info string (for example `bash` or `go`)
renders with highlighting and is easy to copy. Indented code, empty fences, and
Mermaid blocks do not satisfy this rule because Mermaid is evaluated as a visual.
Source: GitHub formatting guidance, standard-readme examples.

**prerequisites.** Runtime versions, services, and environment needs are a
common source of failed first runs. The rule accepts a heading or an explicit
sentence such as "requires Go 1.24". It is informational because some projects
genuinely have no prerequisites. Source: Make a README, standard-readme.

### Visuals

| ID | Severity | Weight | What passes |
| --- | --- | --- | --- |
| `visual` | info | 5 | A screenshot, GIF, or Mermaid diagram is detected. |
| `image-alt` | warning | 5 | Every Markdown/HTML image has non-empty alt text; skipped when no images exist. |

**visual.** Screenshots, animated demos, and diagrams communicate interface and
architecture quickly. Detection is heuristic: Mermaid blocks, GIFs, images with
screenshot/demo/preview/example/usage markers, and non-badge raster images
qualify. Logos, icons, avatars, badges, and SVGs do not count on their own.
Source: Awesome README, Make a README.

**image-alt.** Alt text is the accessible name of an image and remains useful
when an image fails to load. Both Markdown `![alt](src)` and HTML `<img alt>`
are inspected, including images inside raw HTML blocks. Source: W3C WAI alt
decision tree, WCAG non-text content.

### Trust and maintenance

| ID | Severity | Weight | What passes |
| --- | --- | --- | --- |
| `license-file` | error | 7 | A LICENSE/LICENCE/COPYING/COPYRIGHT file exists at the root. |
| `license-mentioned` | warning | 4 | The README has a license section or mentions licensing. |
| `ci-workflow` | warning | 5 | GitHub Actions reports at least one workflow. |
| `badges-valid` | warning | 5 | GitHub Actions CI badges reference existing workflow files; skipped when no such badge exists. |
| `not-archived` | info | 1 | The repository is not archived. |

**license-file.** A repository without a license leaves users without clear
permission to use and redistribute the code. The root listing is checked rather
than trusting only GitHub's detected license metadata. Source: GitHub licensing
docs, Choose a License.

**license-mentioned.** Users should not have to open another file to learn the
basic reuse terms. A License/Lizenz heading or an explicit license sentence
passes. Source: standard-readme, GitHub licensing docs.

**ci-workflow.** A workflow is evidence that changes are checked automatically.
The rule is skipped if the Actions API is unavailable, so a permission problem is
not reported as a missing workflow. Source: GitHub Actions docs.

**badges-valid.** A CI badge that points to a missing workflow is a false health
signal. readmecheck extracts GitHub Actions workflow badge URLs (including the
common shields.io status form) and compares the referenced filenames with the
repository's workflow list. Badges for other repositories are not verified and
the rule is skipped when no own-repository CI badge is present. Source: GitHub
workflow status badges.

**not-archived.** Archived repositories are read-only, which changes how a
visitor should evaluate them. This is informational rather than a defect: a
finished project may be intentionally archived. Source: GitHub archiving docs.

### Contribution

| ID | Severity | Weight | What passes |
| --- | --- | --- | --- |
| `contributing` | info (warning for ≥1,000 stars) | 4 | A CONTRIBUTING file or non-empty contribution heading exists. |

**contributing.** Contribution guidance explains how to report bugs, propose
changes, run tests, and behave in the community. The file can live at the root,
under `.github/`, or elsewhere with a `CONTRIBUTING*` basename. For larger
projects (1,000+ stars) the result's severity is raised to warning. Source:
GitHub contributor guidelines, Open Source Guides.

### Hygiene

| ID | Severity | Weight | What passes |
| --- | --- | --- | --- |
| `no-empty-sections` | warning | 4 | No heading is followed directly by another heading. |
| `no-placeholders` | error | 6 | No TODO, Lorem ipsum, "Project Title", or similar template text is found. |
| `reasonable-length` | warning | 3 | The README has at least 60 words and is not over 20,000 words/150,000 characters. |
| `table-of-contents` | info | 2 | A README with 8+ H2/H3 sections has a TOC or 3+ anchor links. |

**no-empty-sections.** Empty headings look like abandoned work and make the
document hard to navigate. Any heading immediately followed by another heading
fails, regardless of heading level. Source: editorial guidance from
standard-readme.

**no-placeholders.** Template artifacts shipped to production make a project
look unfinished and can mislead readers. The check is case-insensitive and looks
for TODO, Lorem ipsum, Project Title, One Paragraph of project description,
insert description here, and your project name. Source: Make a README, Awesome
README anti-patterns.

**reasonable-length.** The thresholds are deliberately generous. Under 60 words
rarely covers purpose plus installation plus usage. Over 20,000 words (or
150,000 characters) usually means reference material belongs in `docs/`. Source:
general guidance from Make a README and standard-readme; thresholds are
editorial.

**table-of-contents.** Long READMEs need an outline. A dedicated TOC heading or
three anchor links passes. Short READMEs pass automatically rather than being
marked skipped, because the rule's condition is "if long, then TOC". Source:
Awesome README, standard-readme.

### Links

| ID | Severity | Weight | What passes |
| --- | --- | --- | --- |
| `relative-links` | error | 8 | Every relative link target exists in the repository tree. |
| `external-links` | warning | 5 | Every checked external link responds; skipped when checking is disabled. |

**relative-links.** Relative links connect a README to guides, licenses, and
examples; moved files silently break them. The implementation resolves `.`,
`..`, URL encoding, fragments, queries, and root-relative paths, then checks the
repository's recursive git tree. The check is skipped if GitHub does not return
a complete tree. Source: GitHub relative-link formatting guidance.

**external-links.** External references rot. The GUI enables or disables this
optional check. When enabled, links are deduplicated and checked with eight
concurrent workers, a five-second per-link timeout, and a 50-link cap. A HEAD
request is used first with a GET fallback for 403/405/501 responses. Statuses
2xx/3xx are reachable; 401, 403, and 429 count as reachable but restricted
because the host answered. 404/410, other 4xx, 5xx, and network failures count
as unreachable. The result lists sample failures. Source: link-checking is an
operational practice rather than a README style rule.

## Deliberate exclusions

- **CHANGELOG**: useful for libraries but not universally required.
- **Release notes**: the latest release is fetched for context but not scored.
- **Badge count**: more badges do not mean a better README.
- **Exact section order**: different project types need different structures.
- **Language correctness**: this is not a grammar checker.
- **External badge health**: only GitHub Actions workflow targets are verified
  locally; other badges are covered indirectly when external links are checked.
- **Any AI/LLM judgment**: out of scope by design.
